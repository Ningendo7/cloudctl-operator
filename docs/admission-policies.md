# Admission policies

The chart can install `ValidatingAdmissionPolicy` rules that refuse risky
`AppDependencies` before anything reaches AWS. They run inside the API server,
so there is no webhook to keep up. They need Kubernetes 1.30 or later and are
off by default.

```bash
helm upgrade --install cloudctl-operator oci://ghcr.io/ningendo7/charts/cloudctl-operator \
  --set policies.enabled=true
```

`policies.action` starts as `Warn`: the request goes through and the user sees
the message. Watch what would be refused, then set `Deny`. `Audit` only records
it in the API server's audit log.

A request is judged only when it creates a CR or changes its spec, so a CR can
always be deleted, whatever its namespace's labels or the limits now say.

| Rule | Refuses | Labels it reads |
|---|---|---|
| `namespaces` | CRs in a namespace without `cloudctl.io/enabled=true` | `policies.namespaces.label` |
| `limits` | An RDS `instanceClass` outside the list, `allocatedStorage` or `maxAllocatedStorage` over `maxStorage` | `policies.limits.profileLabel` |
| `production` | `force: true` and `deletionPolicy: Delete` | `policies.production.label`, `policies.production.values` |
| `encryption` (off by default) | Resources without `encryption`, and an RDS instance that opts out of it | none |

Every rule applies to every namespace except `production`, which applies to the
namespaces carrying its label, and `limits` profiles, below.

**Labels are set by whoever creates the namespace**, normally a platform admin
or the GitOps manifest of the `Namespace`. A missing label means "not
production". Anyone who can edit a `Namespace` can change its labels, so the
rules hold only if your teams cannot.

## Limits per team

A namespace labelled `cloudctl.io/policy-profile=<name>` gets that profile's
numbers instead of the defaults:

```yaml
policies:
  limits:
    rds:
      maxStorage: 500
    profiles:
      large:
        rds:
          maxStorage: 2000
```

A profile leaves out what it does not change.
